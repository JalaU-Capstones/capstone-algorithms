# Data Model Design

> Student Performance Analysis System | August 2026

---

## 1. Entity: StudentRecord

**Purpose:** Represents a single student performance evaluation entry. Each record captures
the student's name, the subject they were evaluated on, their numeric score, and their
assigned skill-level category. The table is the sole persistent entity in the system and
provides the data set for all search, sort, and statistical operations.

---

## 2. Field Reference

| Field | Type | Constraints | Description |
|---|---|---|---|
| `id` | `INTEGER` | Primary Key, Auto-increment, Not Null | Unique surrogate identifier for the record. Generated by the database; never set by application code. |
| `name` | `VARCHAR(100)` | Not Null | Student's full name. Must be non-empty and at most 100 characters. |
| `category` | `VARCHAR(50)` | Not Null | Skill level classification. Accepted values: `Junior`, `Mid`, `Senior`, `Expert`. |
| `score` | `NUMERIC(5, 2)` | Not Null | Evaluation score. Must be in the range **0.00 – 100.00** (inclusive). Stored with two decimal places. |
| `subject` | `VARCHAR(100)` | Not Null | Name of the evaluated subject or course. Must be non-empty and at most 100 characters. |
| `created_at` | `TIMESTAMP` | Not Null, Default `now()` | UTC timestamp set automatically when the record is inserted. Never modified after creation. |

## 3. ASCII ER Diagram

```text
┌───────────────────────────────┐
│       student_records         │
├───────────────────────────────┤
│ PK  id         : INTEGER      │
│     name       : VARCHAR(100) │
│     category   : VARCHAR(50)  │
│     score      : NUMERIC(5,2) │
│     subject    : VARCHAR(100) │
│     created_at : TIMESTAMP    │
└───────────────────────────────┘
```

> **Note:** The system uses a single-table design. There are no foreign keys or
> relationships. This flat schema is intentional — it provides a realistic data set
> (strings, decimals, timestamps) while keeping the focus on algorithm implementation
> and complexity analysis rather than relational modelling.

---

## 4. Validation Rules

| Field | Rule |
|---|---|
| `name` | Non-empty string; maximum 100 characters; leading/trailing whitespace is stripped before insertion. |
| `category` | Must be one of exactly four values: `Junior`, `Mid`, `Senior`, `Expert`. Any other value is rejected by the service layer before reaching the repository. |
| `score` | Numeric value; must satisfy `0.00 ≤ score ≤ 100.00`. Values outside this range raise a `ValueError` in the service layer. |
| `subject` | Non-empty string; maximum 100 characters; leading/trailing whitespace is stripped before insertion. |
| `created_at` | Set automatically by the database default (`now()`). The application never writes this field directly. |

---

## 5. Migration Strategy

Database schema changes are managed exclusively through **Alembic versioned migrations**
located in `migrations/versions/`. This approach guarantees that:

- The database state is fully reproducible from any checkout of the repository.
- Schema history is version-controlled alongside application code.
- CI/CD environments (GitHub Actions) can bring a fresh PostgreSQL instance to the
  correct state with a single command: `uv run alembic upgrade head`.
- Rolling back to a previous schema version requires only: `uv run alembic downgrade -1`.

The initial migration (`c189d604bd7f_create_student_records_table.py`) creates the
`student_records` table with all fields and constraints described above.

---

## 6. DTO Pattern

The application uses a **Data Transfer Object (DTO)** — `StudentRecordDTO` — implemented as
a Pydantic model in `src/capstone/models/__init__.py`. This object is the currency that
flows between all layers above the database:

- The **Repository layer** maps SQLAlchemy ORM objects (`StudentRecord`) to
  `StudentRecordDTO` instances before returning them to callers.
- The **Service layer** works exclusively with `StudentRecordDTO` objects; it never imports
  or references SQLAlchemy models.
- The **CLI layer** receives `list[StudentRecordDTO]` from the service and renders them with
  `rich` — it also never touches ORM objects.

**Benefit:** Changes to the ORM mapping or the database schema are isolated to two files
(`models/record.py` and `repository/record_repository.py`). The rest of the application is
insulated from any persistence-layer change.
